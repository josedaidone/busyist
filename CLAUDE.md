# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

buZyist (spelled with a capital Z in anything people read; called Busyist before 1.5.0) is a Windows-only tray app that runs Todoist pomodoros on a BUSY Bar (a hardware timer), or on the PC when there is no bar. Python backend (the `buzyist/` package, started by `busyist.py`) + pywebview/WebView2 UI (`ui/`).

## Commands

```powershell
# Run from source (Python 3.11+, Windows). --show opens the window instead of starting in the tray.
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe busyist.py --show      # or run.bat (pythonw, no console)

# Build installer + portable zip + SHA256SUMS into dist\ (needs Inno Setup 6; -SkipInstaller to skip it)
powershell -ExecutionPolicy Bypass -File build.ps1

# Tests and lint (dev tools pinned in requirements-dev.txt; config in pyproject.toml)
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pytest
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m ruff format .
```

- Tests (`tests/`, pytest): `tests/conftest.py` isolates every run. Autouse fixtures point every path under `DATA_DIR` into `tmp_path` and allow only loopback sockets, and an audit hook refuses (and fails the test on) any write under the real `%APPDATA%\Busyist`. A new `*_PATH` under `DATA_DIR` (in `buzyist/paths.py`) is picked up automatically; add it to `EXPECTED_DATA_PATHS` there too. Opt-in fixtures: `clock` (fake time behind every app module's `time`/`datetime`/`date` and busylib's `timer_state`), `app`/`make_app` (an `App()` on the local clock with a `FakeTodoist`, nothing started; drive it with `app.engine_step()`), `deferred_threads` (run what the app hands to threads with `run_pending()`), `focus_server` (`FocusServer(app, port=0)` plus a request helper), `side_effects` (beeps, URLs, processes recorded). Mark Win32-only tests `@pytest.mark.windows_only`.
- Ruff: `ruff check .` and `ruff format --check .` must stay clean. Every ignored rule and every `# noqa` carries its reason. `.git-blame-ignore-revs` lists the formatting commit (`git config blame.ignoreRevsFile .git-blame-ignore-revs`).
- CI (`.github/workflows/ci.yml`, every push and PR, windows-latest): ruff check/format, pytest with coverage, `node --check` on `extension/*.js` and `ui/*.js`, `node --test "tests/js/**/*.test.{js,mjs,cjs}"` when `tests/js/` exists, and a manifest check. On PRs it fails when `extension/` changed but `extension/manifest.json`'s `version` didn't. `release.yml` calls it (`workflow_call`) before building.
- Workflow hardening: every `uses:` is pinned to a full commit SHA with a `# vX.Y.Z` comment (Dependabot, `.github/dependabot.yml`, bumps them); workflows start from `permissions: {}` and each job asks for its own. In `release.yml` the `build` job (runs `build.ps1`, pip, Inno Setup) has `contents: read` and `persist-credentials: false`; only `publish` (no checkout, no repo code: downloads the artifact, checks `SHA256SUMS.txt`, creates the release) has `contents: write`. Inno Setup is installed from the official release, pinned by `INNO_VERSION`/`INNO_URL`/`INNO_SHA256` at the top of `release.yml`. New build steps (e.g. signing) go in `build`, never in `publish`.

- Logs go to `%APPDATA%\Busyist\busyist.log` (only a console when run with `python`, not `pythonw`).
- Release: bump `__version__` in `busyist.py` in a PR; merging it into `main` publishes it (`release.yml`'s `version` job releases a version with no `vX.Y.Z` tag yet, refuses one older than the latest tag, and the `publish` job creates the tag on the merged commit; merges without a bump publish nothing). A hand-pushed tag `vX.Y.Z` still works and fails if it differs from `__version__`; `build.ps1`, the PyInstaller spec and the Inno script all read the version from that one line by regex, so keep its `__version__ = "x.y.z"` format.
- The in-app updater depends on the release assets: it looks for `Buzyist-Setup-<version>.exe` (falling back to `Busyist-Setup-<version>.exe`) and `SHA256SUMS.txt` on the GitHub "latest release", so keep those names. `build.ps1` also copies the installer to `Busyist-Setup-<version>.exe`, because copies from before the rename only look for that name. It runs the new Setup with `/VERYSILENT /RELAUNCH=1`, and `DeinitializeSetup` in `packaging/busyist.iss` starts the app again afterwards.
- **The rename**: `APP_NAME = "buZyist"` is what people see (window titles, tray, notifications); `APP = "Busyist"` stays for the data folder `%APPDATA%\Busyist` (Chrome loads the unpacked extension from there, so moving it would orphan the extension), the sign-in Run value and the logger. The exe is `Buzyist.exe`; the Inno `AppId` is unchanged so Setup installs over old copies, removes `Busyist.exe` and its shortcuts, and repoints an old Run entry. The extension id (manifest `key`), the repo name and `busyist.py` keep their names; the package is `buzyist/`.
- `build.ps1` aborts if `config.json`/`session.json`/`history.json` end up in `dist\`. Those files are gitignored personal data (tokens, PIN); never commit them.

## Architecture

`busyist.py` is only the entry point: `__version__` (the line the build reads), `busyist.App` and `main`. Run as a script it registers itself as the `busyist` module before anything else, so `constants.app_version()` reads its `__version__` without loading it a second time. The app is the `buzyist` package (the new name with a Z; `busyist.py`, the data folder, the logger and the repo keep the old one), one module per part. Rules the split depends on:

- **Paths are read at call time**: `from buzyist import paths`, then `paths.CONFIG_PATH`; never `from buzyist.paths import CONFIG_PATH`. The tests' `data_dir` fixture rebases the Paths in `buzyist.paths` and fails a test when any other module holds a copy of one.
- Every module logs to `logging.getLogger(APP)`, the `"Busyist"` logger.
- `webview`, `pystray` and `winsound` are imported only by `app.py` and `tray.py` (`win32/windows.py` names `webview` for type hints only). The rest imports the standard library plus busylib (`bar.py` with httpx2, and the App modules), pydantic (`config.py`) and Pillow (`tray.py`); on another OS the `win32` handles are None, so those modules still import.
- A module that replaces something in a test must patch it where it is looked up: a name imported with `from x import y` lives in the importing module. `conftest.patch_everywhere(monkeypatch, name, value)` sets it in every app module that has it (`app_modules()`), which is how the `clock`, `deferred_threads`, `side_effects` and registry fixtures patch `time`/`datetime`/`date`, `threading`, `winsound`, `subprocess`, `message_box`, `set_launch_at_login`, `winreg` and `Todoist`.

- **Todoist** (`todoist.py`): thin REST client (`api/v1`, paginated) for tasks by filter query, labels, comments, close.
- **Bar** (`bar.py`): the BUSY Bar over Wi-Fi and/or USB (`USB_ADDR` = `10.0.4.20`) via `busylib`. Every call goes through `Bar.run`, which holds one RLock and tries the last-working route first. The bar has no "start timer" command: the app writes a whole *snapshot* (`BusySnapshotInterval` / `NotStarted`) and the bar ignores any snapshot whose timestamp isn't newer than its own, hence `Bar._write` using `max(now, live+1)`. Pause/stop/skip are read-modify-write snapshot edits (busylib's helpers are async-only, so they're reimplemented synchronously). The bar refuses fewer than 2 work phases, so a 1-round session runs as `BAR_CYCLES_MIN` on the bar and the app stops it at the first break.
  - **No bar**: with `use_busybar` off (the default for new installs; configs saved before the setting existed are migrated to `True` by `migrate_pre_versioning` in `config.py`), `Bar.run` hands every call to a `LocalClock` instead of a `BusyBar` client. `LocalClock` implements only `busy_snapshot`, `busy_snapshot_set` and `busy_profile`, and keeps the last snapshot in `timer.json`; `timer_state` does the arithmetic, so the same start/pause/skip/stop code and the engine work unchanged. A new bar call used inside `Bar` needs a `LocalClock` counterpart. Switching modes while a session runs is refused (`save_settings`: the session's stamp belongs to the old source). `state()["bar"]["local"]` tells the UI which mode it is in.
  - **Bar out of reach** (empty battery, out of range): after `BAR_OFFLINE_AFTER` failed polls (`BarUnreachable`), or at once when a start/pause/resume/skip/stop can't reach it (`SessionMixin._on_bar`), `App.go_standalone` → `Bar.go_offline` copies the bar's last snapshot (`Bar.last`, or timer.json after a restart if it isn't older than the session) into the `LocalClock`, and `Bar.run` uses that clock while `Bar.offline` is set (`Bar.standalone` = local or offline; `state()["bar"]["offline"]`). `Bar.poll` (the engine's read) looks for the bar every `BAR_PROBE_S` and `_take_back` writes what the clock holds back to it (the time left now, the bar's card, at least `BAR_CYCLES_MIN` cycles); with nothing running and nothing done here, a bar that changed meanwhile keeps its own state. With no snapshot to start from, `control("stop")` still ends the session.
- **No Todoist**: `use_todoist` off (or no token) means `App.todoist_on` is false. `start_task(None, name)` (`session.py`) then starts a session with an empty task id (`content` = the name or "Focus session"); `finish`/`_label_task` skip every Todoist call when the id is empty. With `use_todoist` off the UI adds `body.solo` (task list hidden) and `Api.set_solo` resizes the main window to `SOLO_W`×`SOLO_H`.
- **App** (`app.py`): owns state, guarded by `App.lock`; every attribute is set in `App.__init__`, and the mixins it inherits hold methods only. Lock order is `bar.lock` then `app.lock` (see `start_task`), and the config lock (`ConfigStore`) then `App.sync_lock` (see `save_settings`, `apply_sync`). **`App.cfg` is a `ConfigStore`** (`config.py`; copy-on-write, shared with `Todoist` and `Bar`): read with `cfg.get(k)`/`cfg[k]`, or `cfg.view()` for a consistent dict when reading several keys, and never mutate what they return; change settings only inside `with self.cfg.edit() as c:` (a deep-copied draft that replaces the whole dict and is saved to `config.json` when the block ends; an exception discards it, an unchanged draft writes nothing). The **engine thread** (`App.engine`/`engine_step`) polls the bar's snapshot every `poll_seconds` (every 1s in no-bar mode), then `follow_session()` derives session progress *from the bar's state*, not from a local timer: even interval indices are work, odd are rest; "finished"/"stopped" are inferred from the snapshot, and snapshots older than `session["stamp"]` are ignored. When a session ends, `finish()` runs on its own thread (Todoist comment, optional label removal, history append, "complete task" prompt). The running session is persisted to `session.json` so a restart resumes it (`self.recovering` makes that end silently). `App.run` creates the windows, the tray, the hotkey and the threads. The mixins:
  - `session.py` (`SessionMixin`): `start_task`, `control` (pause/resume/skip/stop), `follow_session`, `finish`, `complete_task`, `_label_task`.
  - `app_sites.py` (`SitesMixin`): `site_focus` (what `/focus` answers), `note_extension`, `extension_connected`/`extension_outdated`, `site_limits_status`, `record_usage`, `grant_pass`.
  - `app_sync.py` (`SyncMixin`): `sync_payload`, `apply_sync`, `_merge_limits`, `note_instance`, `note_limits_edit`, `shared_session`, `remote_session`, `sync_info`; the comment above `sync_on` describes the merge.
  - `app_updates.py` (`UpdatesMixin`): `updater` (the thread), `check_for_update`, `install_update`, `report_update`, `idle_for_update`, `update_view`.
  - `app_windows.py` (`WindowsMixin`): `show_main`, `hide_main`, `show_mini`/`hide_mini`, `cycle_windows` (the hotkey), `tell_visible`, `on_closing`/`on_minimized`, `quit`.
  - `tray.py` (`TrayMixin`): `notify`, `update_tray`, `make_tray`.
- **Api** (`api.py`): the object exposed to JS as `window.pywebview.api.*`. Every method goes through `Api._do`, which returns `{ok, ...}` / `{ok: False, error}` and turns `AppError` into a user-facing message. Raise `AppError` for expected failures.
- **Win32** (`win32/`): `win32/__init__.py` declares the argtypes/restype of every call the app makes, once, on private `user32`, `kernel32` and `crypt32` handles (`ctypes.WinDLL(..., use_last_error=True)`), with named constants (`SW_HIDE`, `WM_MOUSEMOVE`, `SPI_GETWORKAREA`, ...) and the structures the prototypes take (`PROCESSENTRY32W`, `DATA_BLOB`, `INPUT`). The other modules import those handles and only call them; nothing sets prototypes elsewhere or uses the shared `ctypes.windll` (whose prototypes pywebview and pystray rely on). A new Win32 call is declared there first.

**Updates** (`app_updates.py`, with `updater.py` and `updater_sign.py`; packaged builds only): every 6 h (`UPDATE_EVERY`) it asks GitHub for the latest release. A Setup-installed copy (`unins000.exe` next to the exe, `UPDATABLE`) that the user can write to (`app_dir_writable`) downloads the installer, checks it against `SHA256SUMS.txt` and installs it once nothing is going on (no session, no end-of-session summary, window closed). It then quits so Setup can replace its files. All-users installs don't install on their own: they notify, and the Install button goes through an admin prompt. Portable copies only link to the release. `update.json` in the data folder records the target version so the next start can report whether the update worked. Before running Setup, `install_update` locks the file (`open_locked` in `win32/files.py`, `CreateFileW` with `FILE_SHARE_READ` only), hashes it again through that handle and starts it with the handle still open (#004). Signing (#022): when `UPDATE_PUBKEYS` (in `updater.py`) is non-empty, `SHA256SUMS.txt` must carry a valid minisign signature (`SHA256SUMS.txt.minisig`, pure-Python Ed25519 in `updater_sign.minisign_verify`) or the update is refused; while it is empty only a warning is logged. Download URLs must be under this repo's `/releases/download/` (`check_release_url`). `tools/minisign.py` makes keys and signs; its `--app busyist.py` finds `UPDATE_PUBKEYS` in `buzyist/updater.py` next to it. See `docs/RELEASING.md`.

**App blocker** (issue #1, `blocker.py`): `AppBlocker` closes (or hides to the tray) the apps in `blocked_apps` during a work phase, using the same `App.focus()` rule, and reopens the ones that had a window when focus ends. `PROTECTED_EXES` (Windows itself, buZyist, the browsers) are never closed, even if added by hand; the list is mirrored in `ui/main.js` (a test checks they match). `running_apps()` (this user's programs, windowed first, minus `%SystemRoot%`; `Api.running_apps`) feeds the program names suggested under the Apps tab's input and the app-limit editor (`suggestApps` in `ui/main.js`).

**App limits** (`app_limits.py`, `app_limits_on`/`app_limits`, off by default): the site limits' budgets and blocked hours (`clean_limit_times` in `site_rules.py`, shared by both cleaners) for Windows programs, `{id, apps, action, remind, enabled, budgets, windows}` (`remind`: minutes between beeps, `APP_LIMIT_REMIND_MIN`..`MAX`, mirrored in `ui/main.js`; `DEFAULT_APP_LIMITS` in `constants.py`, WhatsApp and Slack beeping, with fixed ids). `AppLimiter` (its own thread, asleep while there are no rules in force; `save_settings` pokes it) counts every `TICK` the program in front (`foreground_app`, `win32/windows.py`) unless the PC has been idle `APP_IDLE_S` (`idle_seconds`, `win32/input.py`), into a second `SiteUsage` (`App.app_usage`, `app_usage.json`); `app_limit_status` is `site_limit_status` with the apps' names as `pattern`. A reached `"close"` rule closes its apps like the app blocker (WM_CLOSE, then end after `CLOSE_GRACE`; `PROTECTED_EXES` refused on save for close rules, skipped when enforcing), in front or not, with one toast per block; a `"beep"` rule only `App.alert`s (beep + toast) while one of its apps is in front, again every `remind` minutes. Not shared through Chrome sync. The Limits tab edits both kinds with the same code (`LIMITS` in `ui/main.js`); `Api.app_usage` feeds its bars. Tests: `tests/test_app_limits.py`.

**Site blocking** (issue #2, `focus_server.py`, `app_sites.py`, `site_rules.py`, `extension.py`): `FocusServer`, a `http.server.ThreadingHTTPServer` on `127.0.0.1:47616` (next to the single-instance socket on 47615) serves `GET /focus` → `App.site_focus()` (`{active, task, ends_at_ms, mode, patterns, sites}`, the same work-phase rule as the app blocker but gated on `block_sites`). It 403s any request whose `Host` isn't `127.0.0.1:<port>`/`localhost:<port>` (DNS rebinding) or whose `Origin` is set to anything but our pinned `chrome-extension://<EXTENSION_ID>` (the extension's own requests may carry no Origin), so a web page can't read the current task. A page can still fire a plain GET with no Origin (an `<img>`), so requests must carry `X-Buzyist: 1` to register a profile (`note_instance`), take or act as `sync_owner`, receive `sync` or post `/sync`; a page can't add that header without a preflight, which is refused. Requests without it (extensions ≤ 1.6.0) still get the blocking payload, can post `/usage`/`/grant`, and still update `extension_version`/`extension_last`, so old extensions get the "Reload extension" notice. Tests: `tests/test_focus_server.py`. The Chrome MV3 extension in `extension/` (manifest `key` pins the id) polls it and uses `declarativeNetRequest` to redirect sites to its `blocked.html`: `site_mode` `"block"` blocks `blocked_sites`, `"allow"` blocks everything except `allowed_sites` (a catch-all redirect rule plus higher-priority allow rules). `patterns` is the active list; `sites` (plain domains of a blocklist only) is kept for extension builds older than 1.1.0. `EXTENSION_SRC` (`extension/`) ships via `datas` in the spec; the packaged app copies it at startup (`sync_extension`) to `EXTENSION_DIR` = `%APPDATA%\Busyist\chrome-extension`, a stable path that survives updates (from source, `EXTENSION_DIR` is the repo folder). `Api.install_extension` copies that path to the clipboard, selects it in Explorer and opens `chrome://extensions` (Edge as fallback, `find_browser`) for "Load unpacked". Site entries are host[/path] patterns where `*` is a wildcard (`*.google.com`, `google.*`, `youtube.com/shorts/*`; a plain host also covers subdomains), validated by `clean_blocked_sites`/`clean_site_pattern` (mirrored by `cleanSitePattern` in `ui/main.js`) and turned into RE2 regexes by `patternRegex` in `extension/background.js`.

**Site limits** (`site_rules.py`, `usage.py`, `app_sites.py`): per-website time budgets and blocked hours, enforced all day whether or not a pomodoro runs, gated by `site_limits_on`. `site_limits` is a list of rules `{id, patterns, enabled, budgets: [{minutes, every, unit, days}], windows: [{days, from, to}]}` (`clean_site_limit`; periods are clock-aligned local time, see the comment above `_hhmm`). The extension measures time on the active tab of the focused, non-idle window and POSTs `{usage: {ruleId: {epochMinute: seconds}}}` to `/usage` (`POST /grant` is the block page's "allow 2 more minutes" pass); both answer with the same payload as `/focus`, whose `limits` array comes from `site_limit_status` (`remaining_s`, `limit_end_ms`, `windows_ms`, ...). `SiteUsage` stores per-minute slices for 2 days, per-day totals after that, in `usage.json`. The extension decides `limitState` itself from the last answer plus time measured since, so it keeps enforcing when Busyist is closed (the last answer is cached in `chrome.storage.local`, unsent usage is kept and sent later). The extension reports its manifest version (`?v=` on GET, `version` in POST bodies); Busyist compares it with the bundled one (`EXTENSION_VERSION`, `extension.py`) and, when older (an extension from before it reported counts), shows a "Reload extension" chip, a reload walkthrough in the Websites tab and one toast, because Chrome doesn't reload an unpacked extension after its files change: **bump `version` in `extension/manifest.json` whenever the extension changes**. The toolbar badge shows the time left on the active tab's limit (else the pomodoro minutes) and `extension/popup.html|js|css` is the toolbar popup (pomodoro, limits, help text when Busyist is closed or nothing is set up); it gets everything from the worker's `popupData`. Limit redirects (`?l=<ruleId>&u=`) sit at priority 3, above allow rules, below focus blocks in block mode (4).

**Block stats** (`blocks.py`, the Stats tab): `blocked.js` tells the worker once per block page (`history.state` keeps a reload from counting again) and the worker queues `{id, at, kind, host}` in `blocks` (`chrome.storage.local`, 3 days, 500 at most) and sends them in `/usage` bodies; `BlockLog.add` counts each id once. Answers carry `blocks_today` for the popup's "Blocked today" card (plus what isn't sent yet, `blocksToday`); `Api.block_stats` feeds the tab (30 days of stacked bars, totals, top sites).

**Sharing limits across PCs** (`sync_limits`, off by default; `app_sync.py`, `sync.py`, `usage.py`): the rules and the time spent on them travel through `chrome.storage.sync`, which only the extension can reach. Each extension profile sends a random `instance` id (`?i=` / body) and its Google account (`identity.email` permission); one profile per PC, `sync_owner` (the first to connect, or picked in Limits settings), gets a `sync` block in its answers (`App.sync_payload`) and posts other PCs' data to `POST /sync` (`App.apply_sync`). Other profiles on the PC enforce and report time as before. Rules merge one by one in `App._merge_limits` (per-rule `at`, tombstones in `deleted`, `on_at` for the switch; state in `sync.json`, read by `load_shared`), never replaced wholesale; time is per PC (`u.<device>.<rule>` keys, `SiteUsage.export`) and `SiteUsage.used` adds the other PCs' (`SiteUsage.remote`, checked by `clean_remote_usage`). The storage layout is described above `shareSync` in `extension/background.js`.

**Sharing the running task** (`sync_session`, off by default; `app_sync.py`): the same owner profile and `/sync` channel (`App.sync_on()` is `sync_limits or sync_session`; the `sync` block only carries `doc`/`usage` when `sync_limits` is on). The PC running a session puts it in `s.<device>` (`App.shared_session`: `stamp` it started with, `snap` = latest bar stamp it saw, task, `work_ms`, `rounds`) and removes it when it ends. Other PCs keep them in `App.remote_sessions` (`clean_remote_sessions`, memory only). `App.remote_session()` matches the bar's timer to one when the bar's snapshot stamp equals its `stamp` or `snap` (same `work_ms`), then stays matched while the stamp only grows; `state()["remote"]` shows it instead of "Started on the bar". It's display only: `self.session` stays None, so that PC never finishes/logs the other PC's session.

Also: the pystray tray icon (`tray.py`, drawn with Pillow, shows minutes left), `GlobalHotkey` (`hotkey.py`, Win32 `RegisterHotKey` on its own thread; the hotkey cycles window → mini → tray, `App.cycle_windows`), launch-at-login via the registry Run key (`win32/registry.py`; from source it runs `paths.SCRIPT`, i.e. `busyist.py`), and single-instance enforcement (`main.claim_single_instance`: a second launch connects to `127.0.0.1:47615`, which makes the first instance show its window, `app.listen_for_second_launch`).

### UI

The look follows the "Tomate" identity in `buzyist-handoff/` (gitignored, local only): its tokens are the `--bz-*` variables at the top of `ui/style.css`, mapped to role variables (`--bg`, `--surface`, `--ink`, `--primary-text`, `--done`, ...) that the components use. Fredoka (display, numbers) and Figtree (text) are embedded from `ui/fonts/` (and `extension/fonts/`), logos are `ui/img/`. No shadows; Tomate is the main action, Manteiga a break, the switch-off grey a pause, Terra "blocked". Small red text uses Molho (`--primary-text`), not Tomate, for contrast. Light only: there is no dark theme (the handoff has none; one was dropped before 1.5.0). `tools/make_icon.py` draws the symbol into `busyist.ico`, `busyist.png` and `extension/icon.png`.


`ui/main.html|js` (main window: task list, saved filters, settings) and `ui/mini.html|js` (frameless always-on-top timer) are plain JS with no build step or framework. Both are separate pywebview windows sharing one `Api`. The pages **poll `get_state()`** (mini: every 1s, interpolating the countdown locally from `state.now`); Python can also push with `window.evaluate_js` (e.g. `window.Mini.refresh`), but failures there are swallowed because the page may not be loaded yet. `Api.get_state` / `App.state()` is the single source of truth for what the UI shows.

### Data and packaging

- Runtime data lives in `%APPDATA%\Busyist` (`config.json`, `session.json`, `history.json`, `timer.json`, `usage.json`, `app_usage.json`, `blocks.json`, `sync.json`, log, `webview/`), never next to the program. `DEFAULTS` in `buzyist/config.py` holds the default of every setting and `Config` (pydantic) is the schema: types, bounds and checks, reusing the `clean_*` validators (a key added to `DEFAULTS` needs a `Config` field too; `tests/test_config.py` checks they match). `Config.load` (start-up) falls back to the default for a key that is still invalid after tidying, with a log line, and `Config.check` (every `ConfigStore` edit, `save_settings`) raises `AppError` with the message Settings shows (`FIELD_ERRORS` for the non-`clean_*` checks). Files carry `config_version`; to change the shape of a saved setting, add a function to `MIGRATIONS` under the next number (it runs once on older files, before validation) and a fixture to `tests/data/configs/`; `adopt_old_files()` (`main.py`) migrates files from the script directory when running from source.
- Data files are written with `write_json` (`storage.py`; own temp file, fsync, rename with retries, one lock per path); `read_json` renames an unparseable file to `<name>.corrupt-<when>` and logs it, and `config.json` then falls back to `config.json.bak` (refreshed at most hourly by the config save). The secrets (`SECRET_KEYS`: Todoist token, bar PIN) are DPAPI-encrypted on disk (`secrets_dpapi.py`) (`dpapi:v1:<base64>`, current Windows user) and plain only in memory; `get_settings` sends `""` plus `has_<key>`/`<key>_lost`, and `save_settings` treats an empty secret as "keep" and `clear_<key>: true` as Remove.
- Resources are found via `paths.RES_DIR` (`sys._MEIPASS` when frozen, else the folder of `busyist.py`, not of the package). New files the app needs at runtime (assets under `ui/` are already covered) must be added to `datas` in `packaging/busyist.spec`; new hidden imports go there too (pywebview/pystray/busylib are loaded dynamically; `collect_submodules("buzyist")` takes in every app module).
- Dependencies are hash-locked with pip-tools. Edit the sources, `requirements.in` (runtime; also declares what the code or the spec uses directly: `httpx2`, `pydantic`, `pythonnet` for `clr`), `requirements-build.in` (PyInstaller) and `requirements-dev.in` (ruff, pytest, pip-tools, pip-audit; it includes the runtime set), never the `.txt` files, then recompile them **on Windows with Python 3.11** (pywebview/pythonnet/pywin32 have platform markers; the build and dev files take `-c requirements.txt`, so compile `requirements.txt` first):
  ```powershell
  .\.venv\Scripts\python.exe -m pip install --require-hashes -r requirements-dev.txt   # brings pip-tools
  .\.venv\Scripts\python.exe -m piptools compile --generate-hashes --strip-extras --allow-unsafe requirements.in
  .\.venv\Scripts\python.exe -m piptools compile --generate-hashes --strip-extras --allow-unsafe requirements-build.in
  .\.venv\Scripts\python.exe -m piptools compile --generate-hashes --strip-extras --allow-unsafe requirements-dev.in
  ```
  Add `--upgrade-package <name>` to move one package, `--upgrade` for all. `build.ps1` installs with `--require-hashes` into a separate `.venv-build`; CI installs `requirements-dev.txt` the same way and runs `pip-audit` on the three lock files. The repo's `old/`, `.webview/`, `.venv*` are local and gitignored.
